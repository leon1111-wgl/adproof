### 9. 红队回合 —— 采纳

**为什么是它。** 规则库是封闭词表，第一轮的盲测首跑召回只有 60.3%，漏的几乎都是“换个说法”。修复只能来自看过的错误，而看过的错误会让同一个集合不再是盲测。红队回合把两件事拆开：生成模型每轮提供**新的**说法，用来找漏洞和写规则；另一个模型家族事先写好、作者没有读过的盲测集，只用来报告质量。

**做法。**

1. **生成**：GLM-4-9B-0414（智谱，MIT 许可，Q4_K_M GGUF）在 GitHub Actions 的 4 核 CPU 上由 llama.cpp 运行。每轮按 9 个分类、每类 2 个虚构商品，写出规避常见关键词的违规说法和合规的近似说法（“最好睡前用”这一类）。输出受 JSON Schema 约束；权重和 llama.cpp 按 URL 和 SHA-256 固定，只在 runner 上下载。
2. **修复前打分**：同一个 Actions 任务里，用这次提交的浏览器引擎（静态演示里审查访客脚本的同一份代码）审每一句。违规说法被同一分类标出算“标出”，近似说法被标出任何东西算“误报”。这个修复前的标出率是每一轮的头条数字，但它是回合统计，不是质量指标：说法由生成模型写、标签由生成模型给。
3. **模型审计**：第三个家族的模型 Qwen3-4B-Instruct-2507（Apache-2.0）按分类口径标注**固定随机抽样**（只由回合编号决定，不看引擎结果），与生成时的标签不一致的比例记为标签噪声率。漏检和误报另外全部送审，只用于分诊。**没有人工审核这些标签**，页面和文档都写“模型审计”，不写“人工复核”。
4. **规则提案**：`proposals.md` 列出每条漏检和误报，以及这一分类在该商品类目下**可以引用的已核对条款**（从本地快照解析，解析不到的标“待核对，不能引用”）。作者在 `decisions.json` 里逐条决定采纳或不采纳并写明理由；采纳的改动单独提交，规则只进入已有分类，所以引用只来自已核对快照。
5. **修复后记录**：每次规则提交后，用同一批说法重审并追加到 `rescores.json`；页面据此显示“哪次规则提交标出了哪条漏检”。`tests/redteam.test.ts` 要求页面上的“当前结果”与这次构建的引擎一致、修复前标出的说法现在没有漏掉、每条漏检都有决定、采纳的都已修复。
6. **质量数字**：`backend/evals/blind_v2.yaml`，60 条虚构脚本，由 Claude Sonnet 只依据分类说明、标注口径和商品资料写成，在本轮任何规则改动之前提交（`792631a`），作者没有读过其中的脚本。报告片段级 P / R / F1，干净脚本误报写在旁边。

**模型选择。** 生成、审计和盲测分别来自三个家族（GLM、Qwen、Claude），审查引擎本身是规则，不是模型。生成模型在 GLM-4-9B-0414（MIT）和 InternLM3-8B-Instruct（Apache-2.0）之间选了前者：许可证最宽松、更新，而且 Q4 文件 6.2 GB 在 16 GB 内存的 runner 上留有余量。审计用 Qwen3-4B-Instruct-2507，因为它在作品集的 LoopDesk 里已经在同一种 runner 上实测过（13.6 token/s）。本仓库的吞吐探测（Actions 运行 42687578661）：GLM-4-9B-0414 生成 4.4 token/s，Qwen3-4B-Instruct-2507 生成 11.5 token/s；一轮 72 句约 30 分钟。

**结果（详见 [EVALUATION.md 第 7 节](EVALUATION.md#7-红队回合v12)）。** 两轮的修复前标出数是 4/54 和 6/54；采纳的 35 条提案让它们升到 24/54 和 19/54，但盲测集 v2 的结果在修复前后**完全相同**（P 83.8% / R 38.8% / F1 53.0%，干净脚本误报 0/18）。流程可复现，规则却只学到了生成模型的说法。这是本轮最重要的结论，页面上也这样写。

**哪里会出错（都写在页面和评测文档里）。** 生成模型的“话术”风格和真实直播文案不同，规则可能只学会了生成模型的说法——盲测集由另一个家族写，就是为了检查这一点；生成的“违规”可能根本不违规——这是模型审计要估计的标签噪声；审计模型自己也会错，它的意见不是金标。

### 10. 浏览器内“疑似”通道（bge-small-zh）—— 本轮不采纳

它的样例应当来自已采纳的红队说法，而这一轮才第一次产生这些说法。没有它们，最近邻通道只能拿作者写的例句做样例，精确率无从估计；在盲测集上量出“规则 + 疑似通道”比规则单独更好之前，多出来的琥珀色提示只会增加审核员的负担。下一轮可以用本轮的采纳项做样例，在新盲测集上量一次。

### 11. 截图和视频帧 OCR —— 本轮不采纳

它需要另一套评测（把测试脚本渲染成字幕图片并标明 SYNTHETIC，报告 OCR 字符准确率和从文本到 OCR 的召回损失），和本轮的评测不共用；一轮只做一件事。

### 12. 用模型给改写稿打分 —— 不采纳

需要有人标注一部分改写稿，才能报告模型评分与人的一致性（Cohen's κ）；本项目没有人工标注者。改写质量门目前是确定性的检查（第一轮收尾），可以复现。

### 13. gpt-oss-safeguard-20b 作审计模型 —— 不采纳

它是“自带政策”的分类模型，形式上适合按分类口径审计；但总参数约 21.5B，在 16 GB 内存的 runner 上很紧，而且审计只需要一个与生成模型不同家族、在同类 runner 上实测过的模型。本轮也没能重新打开它的官方发布页核对（返回 403），所以不引用它的说法。

**这一版对应的做法。**

- **专找规避说法**：Google 说新模型的价值在于拦截“为规避检测而设计”的内容；红队回合每轮专门生成规避常见关键词的说法，在修复前打分。
- **从失败生成测试，修复后重跑**：Decagon 从处理不好的对话生成测试并在修复后重跑，Sierra 用 CI 门禁模拟；这里每轮的漏检在规则提交后用同一批说法重审，`tests/redteam.test.ts` 在 CI 里要求页面记录与引擎一致、已标出的不退化。
- **修复只是提案**：Mamoda 的自动修复先交广告主确认，拒审理由落到具体条文；这里的规则修复以提案形式列出可引用的已核对条款，逐条决定后单独提交。
- **写操作单线程**：Cognition 的结论；生成模型和审计模型只读、只提意见，规则库只由一次次单独的提交修改。

**刻意不同的地方。**

- **规模**：每轮几十条说法，不是数十亿条广告；数字只说明这个演示的规则库，不能和平台的数字比较。
- **只有文本**：没有画面、配音和视频帧（OCR 见第 11 项）。
- **没有密钥、没有 GPU**：9B 的 4 位量化模型在 4 核 CPU 上运行，所以每轮的规模受吞吐限制。
- **没有人工标注**：生成标签只有另一家族模型的抽样审计；平台有大规模的人工审核和申诉数据，这里没有。
- **规则是封闭词表，不是模型**：平台用模型理解意图；这里的模型只负责出题和审计，判断和引用仍来自规则与已核对的法条快照（“引错条款比不引更糟”）。
- **决定由仓库作者做出**，不是法务团队；盲测集是合成数据。

### 1. 规则流水线在浏览器里运行，并与后端保持逐条一致 —— 采纳

**现状。** 上一版静态演示只能回放录制好的示例脚本，访客粘贴自己的脚本会得到“静态演示只能审查录制好的示例脚本”。

**做法。** 后端的审查环节本身是确定性的：归一化匹配的规则引擎、商品事实核对、离线语义模式、证据定位与校验、模板改写和复审。这些都可以移植成 TypeScript，在访客的标签页里运行。移植版不自带任何规则或法条：`scripts/build_browser_pack.py` 先用后端自己的 `RuleSet` 校验规则库（含每条规则的正反例），再把规则、法条快照和离线模式导出成 `pack.json`（约 36 KB）；CI 用 `--check` 防止它过期。`scripts/export_parity_fixtures.py` 让后端在 528 个输入上跑完整流水线（评测集、盲测集、规则正反例、演示样例、覆盖用例、带 emoji / 全角 / 零宽字符的扰动、6000 字的恶意输入、SRT 字幕），`parity.test.ts` 要求浏览器的输出逐字段相同。这是 ProofBI 上一轮“同一份产物两种运行时”的做法（那里是 SQLite WASM）。

**移植中真正要处理的差异**（都有测试）：Python 按码点计偏移、浏览器按 UTF-16 计，引擎统一输出 UTF-16 偏移，凡是比较长度的地方（去重、合并、主片段、编辑排序）改按码点算；Python 的 `\d` 是任意 Unicode 数字，JavaScript 只认 ASCII，统一翻译成 `\p{Nd}`，SRT 时间轴和事实核对的数字按 Python 的 `int()` / `float()` 读；`difflib.SequenceMatcher` 逐行移植。

**为什么不直接在浏览器里跑 Python（Pyodide）。** 下载量在 10 MB 量级，冷启动明显慢于一次审查本身；而这条流水线没有用到需要 Python 运行时的依赖。移植后整个演示的 JS 为 153 KB（gzip）。

**测试证明它必要。** 把否定语境检查改成恒为假，`parity.test.ts` 立刻有 55 个用例失败（本轮开发时实测）。

### 2. 引用必须可归因、可核对 —— 采纳并加严

ALCE（Gao 等，EMNLP 2023）把“生成内容是否被所引材料支持”拆成引用召回和引用精确率两项，并指出即使最好的模型，在 ELI5 上也有约一半回答缺少完整的引用支持。AdProof 的引用不是模型生成的，而是规则 → 条款的映射加快照原文，所以问题变成：**引错条款比不引更糟**。

本轮把这一点写成测试：`coverage.json` 给每个规则分类、每条已核对条款各写一句书面表述和一句直播口语表述，并写明这句话**必须得到的完整引用集合**（含款、项和罚则条款）。测试比较的是集合相等，而不是“包含”：多引一条、少引一条、引到别的类目适用的条款（例如把只适用于保健食品的第十八条用在普通食品上），都会失败。另外，每条显示为“已核对”的引文必须逐字出现在快照里，待核对的依据不带任何正文。

### 3. 《直播电商监督管理办法》—— 部分采纳

国家市场监督管理总局、国家互联网信息办公室令第 117 号，2025-12-18 公布，2026-02-01 施行；规定了直播电商平台、直播间运营者、直播营销人员等主体的义务；第三十七条要求直播间运营者使用人工智能等技术生成的人物图像、视频时依规标识，并持续向消费者提示（2026-11-07 在国家网信办转载的全文中核对）。它与本项目的场景直接相关。

但它不在本地已核对的快照里。本项目的规则是：没有在国家法律法规数据库核对过原文的文件，界面上只能显示“待核对”，不能作为法条引用。本轮没有为它做在线核对，所以只在每次审查的“没有检查”里写明：数字人标识、运营者义务这类要求规则库不检查。纳入它需要先按 [docs/RULES.md](RULES.md) 的复核流程核对原文。

### 4. 《互联网广告管理办法》—— 本轮不采纳

市场监管总局令第 72 号，2023-02-25 公布，2023-05-01 施行，细化了利用互联网直播发布广告、变相发布须经审查的广告等规则。理由同上：原文未核对进快照。它会是下一轮最值得核对的文件之一，已写进路线图。

### 5. 2026 年保健食品虚假宣传专项整治 —— 部分采纳

据央视新闻 2026-04-29 的报道（澎湃新闻转载；本项目没有核对通知原文），市场监管总局开展网络食品、保健食品销售虚假宣传专项整治，为保健食品划出“三条高压线”：严打混淆保健食品与药品、明示或暗示“治病”“防癌”“替代药物”；严打“专家”站台和直播带货中的“剧本式”“演戏式”虚假营销；压实平台责任。

规则库已有对应能力：保健食品必须出现“本品不能代替药物”（广告法第十八条第二款、食品安全法第七十九条，均已核对），与药品比较或替代药物（第十八条第一款第四项）。本轮为它们补了书面与口语两种措辞的覆盖用例，并补上“预防……疾病”“软化血管”“医生都推荐”等措辞。“专家”“医生”“亲测”这类证言的资格与真实性，以及直播是否“剧本式”，纯文字规则判断不了：审查范围里把这些句子单独列出，交给人判断，不给法条结论。

### 6. 面向访客输入的正则：线性时间 —— 采纳（用测试约束）

访客输入现在直接在标签页里执行，最坏情况会卡住页面。V8 有一个实验性的非回溯正则引擎（V8 博客，2021-01），但需要启动参数，网页里用不了；RE2 的 WebAssembly 版会把包体积增加数百 KB。本项目的规则窗口都有上界（`{0,4}`、`{0,10}`），因此选择**用测试约束最坏情况**，而不是换引擎。

新增的 `tests/perf.test.ts` 在 6000 字（后端的上限）的九种恶意输入上跑完整流水线。第一次运行就发现了真实问题：同一句话重复一千遍时，标签页要卡 18–36 秒，后端更是要几分钟。原因不在正则，而在 `difflib`（对重复文本是平方级以上）和证据合并的两两比较。两处都在**后端和浏览器同时**修复，结果不变（见 [CHANGELOG](../CHANGELOG.md)）；现在九种输入在 Node 里都在 60 ms 以内，后端在 1 秒以内。

### 7. 流式安全分类模型（Qwen3Guard-Stream）—— 不采纳

Qwen3Guard 技术报告（arXiv 2510.14276，2025-10）提供了 0.6B / 4B / 8B 的流式变体，可以在生成过程中逐 token 判断风险，对直播实时审核是有意义的方向。不采纳的原因：

- 它的类别是通用安全风险（暴力、色情、违法等），不是广告法的绝对化用语、医疗宣称、收益保证；拿它的输出去引用广告法条款，就是“引错条款”的来源。
- 它是模型，在本项目里同样不能在本机跑推理，浏览器端运行会碰到下一节的全部限制。
- 演示访客提交的是整段脚本，不是逐 token 的生成流；“边播边审”需要 ASR 和视频流，超出静态演示的范围。

### 8. 浏览器端小模型（第二档）—— 不采纳，保持关闭

作品集里已有一份公开的 Qwen3-0.6B（MLC q4f16，WebLLM 0.2.86，约 350 MB、约 1.4 GB 显存）。不在 AdProof 上启用的理由：

- **测不出收益。** 本轮盲测首跑里，离线语义模式单独的 F1 只有 7.3%，几乎全部结果来自规则（规则单独 67.7%、双通道 69.6%）。模型通道的价值是召回规则词表之外的换说法，但每一条模型引用仍要经过证据定位，再落到某个分类、某条条款上；0.6B 模型选错分类，就会把错的条款显示给访客，而这比漏检更糟。在没有一次真实模型的盲测证明它能提高召回又不降低精确率之前，不应该上线。
- **LoopDesk 的实测。** 同一模型在 LoopDesk 的真实浏览器运行中失败（约 11 分钟后 `Grammar matcher rejected the newly sampled token`，SwiftShader），而且按其盲测最多只能多答对 1/150。
- **约束。** 本机不跑模型推理；GitHub Actions 的 runner 上没有可用的 WebGPU，做不了真实浏览器测试；GitHub Pages 每月约 100 GB 的流量软上限，大约只够 290 次首次下载。

**什么测量会改变这个决定**：在 GitHub Actions 上用真实模型（API 或开源权重）跑一次本仓库的盲测，模型通道在不降低精确率的前提下明显提高召回；之后才值得考虑浏览器端的小模型，并且仍然要“模型只挑选、程序陈述事实”。
