# 评测

## 1. 数据集

[`backend/evals/scripts.yaml`](../backend/evals/scripts.yaml)：60 条虚构脚本（SYNTHETIC），覆盖 12 个虚构商品、7 个类目（美妆、普通食品、保健食品、数码、家居、招商加盟、课程培训）。

| | dev | test | 合计 |
|---|---|---|---|
| 脚本 | 30 | 30 | 60 |
| 其中 SRT 字幕 | 5 | 7 | 12 |
| 其中不含违规的干净脚本 | 6 | 7 | 13 |
| 违规片段 | 60 | 64 | 124 |
| 缺少必要声明 | 2 | 2 | 4 |

各类违规片段数（dev / test）：绝对化用语 14 / 11、国家机关名义 2 / 2、疾病治疗与医疗用语 16 / 18、效果保证与虚构效果 7 / 7、数据无出处 5 / 8、贬低其他经营者 3 / 4、收益或结果保证 8 / 7、与商品资料不符 5 / 7。

数据里有意放了几类样本：

- **难负例**：“最近”“第一次”“最好在早上喝”“第一时间发货”“本品不能代替药物”“回购率 32%（数据来源：店铺后台统计）”“最大输出功率 65W”“我们不说最好”；
- **规避写法**：“最*好*用”“ＮＯ．１”“顶 级”；
- **隐含宣称**：“我爸喝了一个月血糖都稳了”“十个人里九个说好”；
- **事实不一致**：脚本写“30%烟酰胺”而资料是 5%，脚本写“降噪深度 45dB”而资料是 35dB。

### 标注方式

标注直接写在原文里：`[[分类|违规片段]]`，加载时去掉标记并计算字符起止位置（`app/evals/dataset.py`），并逐条检查 `text[start:end]` 与标注文本一致。SRT 用例先按字幕解析，再去掉标记、重新计算字幕的字符范围。

### 标注口径

1. 显性违规只标**最小违规表述**：“最好用”“全网最低价”“消炎”“医用级”“98%的姐妹”“稳赚不赔”。紧挨着的比较范围词（全网 / 史上 / 行业 / 同类）算在片段内。
2. 隐含违规标承载这层意思的**最短分句片段**：“喝了一个月血糖都稳了”。
3. 与商品资料不符只标“数字 + 单位”：“30%”“99元”“12小时”。
4. 含“副作用”“疗程”“医生推荐”等医疗术语的，归入“疾病治疗与医疗用语”。
5. 主观夸张但不构成明确违规的表述（“熬夜脸也能救回来”）不标。
6. 必要声明（保健食品“本品不能代替药物”、招商广告风险提示）是文档级标注，单独统计，不计入片段指标。

### 划分协议

- dev 用来调试规则；test 写完之后**没有再据此修改规则**，只用于报告。
- 规则调试记录：在 dev 上补了“调理脾胃 / 肠胃”、疾病预防与治愈表述（MED-04）、“保证”后的动词（增强 / 提高）、“提亮”类量化效果、“没有之一”“首选”、“最”字规则的否定语境、W / dB 等单位的事实核对。
- v1.1 改规则时（清单见第 6 节）没有参考 test 集。前三批改动后片段级 P / R / F1 与上一版相同；收尾轮按主会话探测加的类别规则恰好补上了下面公开的 2 处漏检（“防治脂肪肝”“史上最柔软”），又因为“痘印全没了”这条更短的规则片段，把一处原来命中的隐含宣称变成了边界不匹配（记一个误报和一个漏检）。所以 test 现在是 P 98.0% / R 78.1%，而且 **test 已经不是未看过的集合**。原评测集没有“专利宣称”和“专业人士或代言人推荐”的金标。
- “改写后复审通过”从 v1.1 起不包括“无法自动改写”的稿子：改写稿读不通时不展示、不算通过（第 6.7 节），表里另列。
- **局限**：dev 和 test 由同一作者编写，作者写 test 时已经了解规则的写法，test 的独立性有限，尤其是精确率很可能偏乐观。更可靠的做法是请第二个人独立编写和标注，并计算标注一致性（见路线图）。

## 2. 指标

- **片段级 P / R / F1**：预测与金标“分类相同且字符 IoU ≥ 0.5”记为命中；一对一贪心匹配（按 IoU 从高到低），一条长预测不能同时命中两个金标。报告 micro、各分类和 macro F1。
- **严格边界 F1**：要求起止位置完全一致，用来观察边界是否稳定。
- **定位 F1**：不考虑分类，只看片段位置，用来区分“没找到”和“找到了但分错类”。
- **通道消融**：同一数据只开规则通道（含事实核对）或只开模型通道。
- **改写后复审通过率**：在含违规的脚本中，改写稿复审后没有高、中风险问题且必要声明齐全的比例。
- **金标违规被改写比例**：改写的字符级 diff 是否触及每个金标片段。这一项与审查器无关，可以和复审通过率互相印证。
- **证据不变量**：所有结果的片段等于原文切片；所有标记为已核对的法条引用都能在快照中找到。这两项是硬性要求，不达标时 CLI 直接失败。

全部是规则词表之外的换说法，离线模型的上下文模式也没有覆盖：

| 分类 | 漏检片段 | 原因 |
|---|---|---|

这些漏检正是模型通道应该补上的部分。接入真实模型后，需要重点看这一组样本，以及模型会不会因此带来新的误报。

## 4. 门禁

CI 中运行：

```bash
python -m app.evals.cli --gate 0.80 --rewrite-gate 0.90 --report eval-report.json
```

- test 集片段 F1 低于 80%，或改写后复审通过率低于 90%，退出码为 1；
- 证据不变量（片段与原文一致、法条已核对）任何一条不满足，同样失败；
- 报告（指标 + 逐条结果）作为 CI 产物上传。

门禁阈值是**回归门槛**，在当前结果下方留了余量，用来防止改规则或改代码时把指标改坏，不是质量目标。

## 6. 浏览器内审查（v1.1）

静态演示把访客自己的脚本交给浏览器里的引擎（`frontend/src/engine/`，后端流水线的 TypeScript 移植）。本节说明每个数字测在什么上。

### 6.1 浏览器与后端一致

`scripts/export_parity_fixtures.py --include-blind` 让后端在 528 个输入上跑完整流水线，`frontend/tests/parity.test.ts` 要求浏览器输出逐字段相同：结果片段与偏移（码点换算为 UTF-16）、规则编号、引用（含条、款、项与原文）、必要声明、被拒绝的引用、校验报告、改写编辑、复审轮次、差异、计数与风险等级，以及改写稿的复检。输入包括评测集 60 条、盲测集 60 条、每条规则的正反例、演示样例、覆盖用例、240 条带空格 / 全角 / 零宽字符 / emoji / 装饰符 / CRLF / 截断 / 拼接的扰动、8 条边界输入、8 条 6000 字恶意输入和 SRT 字幕（含全角时间轴与 emoji）。

一致性测试本身有效：把否定语境检查改成恒为假，55 个用例失败。

已知的、没有被一致性测试覆盖的差异：Python 的 `re.finditer` 在一个空匹配之后会在同一位置再找一次非空匹配，浏览器不会；规则库里没有能匹配空串的模式，所以这一点目前不影响结果。

### 6.2 覆盖用例

`frontend/tests/coverage.json`：33 句应当标出的话，9 个规则分类、18 条已核对条款都至少有一句书面表述和一句直播口语表述；每句写明它必须得到的**完整引用集合**（含罚则），测试比较集合相等。另有 19 句易混淆的正常表述（“最好在晚上用”“第一次”“粉丝特供”“本品不能代替药物”“专利号ZL…”“三天发货”等），不得有任何结果或缺少的声明。这些句子由本仓库作者在读过规则之后编写，用来防止回退，不是测量。

### 6.3 盲测

- **集合**：`backend/evals/blind.yaml`，60 条脚本（40 条含违规、20 条干净、5 条 SRT），78 个金标片段，覆盖 9 个分类。由另一个模型（Sonnet）只依据分类说明、标注口径和商品资料编写，没有看过代码、规则或原评测集。数据全部虚构（SYNTHETIC）。
- **协议**：在 `d17ee02` 单独提交后才第一次运行；首跑结果原样保存在 [`docs/validation/blind-first-run-0ff7247.json`](validation/blind-first-run-0ff7247.json)。之后的修复看过了首跑的错误，**复跑不再是盲测**。

| 盲测集，离线确定性模型 | 首跑（盲，`0ff7247`） | 修复后（已看过，非盲） |
|---|---|---|
| 片段 P / R / F1（同类型且 IoU ≥ 0.5） | 82.5% / 60.3% / 69.6% | 91.0% / 78.2% / 84.1%；收尾轮后 94.2% / 83.3% / 88.4% |
| 严格边界 F1 | 51.8% | 63.4% |
| 同类型、有任意重叠即算找到 | 55/78 | 66/78 |
| 与任何金标都不重叠的结果 | 1/57 | 0/67 |
| 干净脚本误报 | 1/20 | 0/20 |
| 改写后复审通过 | 40/40（当时没有改写质量门） | 收尾轮后 32/40，另有 8 份无法自动改写 |
| 证据校验 / 法条核对 | 57/57 · 148/148 | 67/67 · 173/173；收尾轮后 69/69 · 177/177 |
| 通道消融 F1：规则 / 离线模式 / 双通道 | 67.7% / 7.3% / 69.6% | 83.3% / 7.3% / 84.1% |

怎么读这张表：

1. 首跑的“误报”大多不是错标：10 个不匹配的结果里，9 个与同类型的金标重叠，只是片段更短（标“治疗”，金标是“能治疗便秘”；标“专利”，金标是“专利选品系统”），按 IoU 记成一个误报加一个漏检。唯一不与任何金标重叠的是 bl-59 的“夏天最好随身带一支补涂”被标成绝对化用语——这是真正的错标，它引用了不适用的第九条第三项，已修复。
2. 修复后仍有 17 个金标没有按 IoU 命中：5 个是边界不同，12 个是真漏检（见 [CHANGELOG](../CHANGELOG.md) 的“已知缺口”）。
3. 离线语义模式单独只有 7.3%：双通道的效果几乎全部来自规则。

### 6.5 恶意长输入

访客输入在标签页里执行。`tests/perf.test.ts` 用 9 种 6000 字输入（同一个触发词重复、一千处结果、只有数字、没有断句的长句、规避符号、emoji、混合触发词等）跑完整流水线。首次运行时最慢的要 36 秒（Node），后端要几分钟，原因是 `difflib` 和证据合并的两两比较。修复后（后端与浏览器同时）每种都在 60 ms 以内（Node），后端在 1 秒以内。改写差异的新算法在评测集 + 盲测集的 120 条脚本里有 98 条与原来的 difflib 完全相同，其余 22 条文字相同、只是红笔分组不同。

### 6.7 改写质量门（收尾轮）

主会话的探测发现，按规则模板改出来的稿子在访客输入上会坏掉，却仍显示“复审通过”：空字符串、只剩“。”、“史上最保暖的，。”、“存在亏损风险不是梦”、同一句模板重复三次、只剩“买它！”。复审只说明规则不再命中，读不读得通它不管。

现在每份改写稿都要过一道质量门（`rewrite_problems`，后端与浏览器同一份逻辑，一致性测试比较结果）。不通过的稿子标为“无法自动改写，请审核员人工改写”：不展示，`passed` 为假，“采用改写稿通过”在服务端和模拟签发里都会被拒绝。原因逐条写给审核员：

| 检查 | 例子 |
|---|---|
| 除了模板语句和必要声明没有剩下内容 | “这个床垫能治疗腰椎间盘突出。” → “” |
| 标点残缺 | “这件羽绒服是史上最保暖的，。” |
| 出现重复的词 / 同一替换语重复 | “直播间直播间活动价”、模板重复三次 |
| 模板语句落在分句中间 | “存在亏损风险不是梦” |
| 只剩一个半句 | “吃了这个酸奶。” |
| 留下了贬低性的说法 | 删掉“某米的充电宝就是垃圾”后剩“一用就鼓包，买我们的。” |
| 没问题的内容被删掉四成以上 | “这款面霜是全网第一，用过的都说好。” → “用过的都说好。” |
| 删除落在分句中间，留下一两个和原词断开的字 | “行业内独一无二的降噪技术。” → “行的降噪技术。” |
| 分句以“的”开头 | “……的降噪技术。”只剩“的降噪技术” |

同时减少坏稿的来源：兜底模板只用在分句末尾且只用一次，整句的空替换改为删除分句，相邻删除合并并带走多余标点，替换语与前后重叠的字去掉，替换语已经说了的必要声明不再追加。

`tests/rewrite.test.ts` 用独立写的检查（不复用质量门的代码）跑覆盖用例、主会话探测和全部一致性输入：展示出来的改写稿都不空、标点完整、替换语不重复、模板不嫁接。

被拦下的多是整段都是违规宣称的稿子：自动删改后剩不下可用的内容，需要人工改写。这一轮没有新的盲测，也没有第二次独立审阅。

范围决定（第二轮探测）：“吊打某星”这类点名贬低属于贬低其他经营者（第十三条）；保健食品“三甲医院都在用”属于易与药品混淆的医疗用语（第十七条、第十八条第一款第二项）。两类都在规则库范围内，所以由规则标出，改写稿里不再保留。

### 6.8 专家推荐为什么只在两个品类里算问题

广告法第十八条第一款第五项（保健食品不得利用广告代言人作推荐、证明）和第二十四条第一款第三项（教育培训不得利用学术机构、教育机构、专业人士的名义或形象作推荐、证明）都在已核对快照里，所以这两个品类的“专家都在吃”“名校教授推荐”会标出并引用原文。其他品类涉及的第十六条（医疗、药品、医疗器械广告）和第三十八条（代言人的义务）不在本地快照里：按本项目的规则，没有核对过的条款不能作为法条引用，所以在美妆、食品等品类里，专家和代言只作为“需要人工判断”的提示列在审查范围里。

## 7. 红队回合（v1.2）

规则库是封闭词表，修复只能来自看过的错误，而看过的错误会让一个集合不再是盲测。v1.2 把两件事拆开：**生成模型每轮提供新的说法**，用来找漏洞、写规则；**另一个模型家族事先写好、作者没有读过的盲测集**，只用来报告质量。流程和代码见 [ARCHITECTURE.md 第 11 节](ARCHITECTURE.md#11-红队回合v12)，取舍见 [FRONTIER_REVIEW.md](FRONTIER_REVIEW.md#第二轮2026-11-10红队回合)。

### 7.1 每一轮做什么

**没有人工审核生成标签。** 标签噪声只有另一家族模型的抽样估计，页面和文档都写“模型审计”，不写“人工复核”。

### 7.2 吞吐（先测，再定每轮的规模）

吞吐探测 [42687578661](https://github.com/leon1111-wgl/adproof/actions/runs/42687578661)（2 个分类、12 句，回合编号 r0，不计入回合）：GLM-4-9B-0414 生成 4.4 token/s、读提示 16 token/s；Qwen3-4B-Instruct-2507 生成 11.5 token/s、读提示 28 token/s（GitHub 公共仓库的标准 runner，4 核 / 16 GB）。按这个速度，一轮 72 句约 20 分钟生成、10 分钟审计，所以每轮定为 9 类 × 2 商品 × (3 + 1)。

探测之后只改了生成提示（`be8074b`）：只说“避开最直白的词”时，生成模型连这一类的宣称本身也一起避开了（最高级变成了普通夸奖），两句近似说法引用了说不出来源的“数据”。提示现在写明每一类的说法仍然要表达什么、给出商品资料，并要求近似说法里的数据写出具体来源。引擎没有改。

缓存按分支隔离：在一个新的 `redteam-run/*` 分支上第一次运行要下载约 8.7 GB（实测约 13 分钟），同一分支再运行时命中缓存。

### 7.7 局限

- **两轮之后，盲测质量没有变。** 这一版证明的是流程（出题、修复前打分、审计、逐条决定、单独提交、修复记录、盲测把关）可以复现，不是规则变好了。下一步应当让生成模型模仿盲测集作者那类说法（例如把宣称借顾客之口、拆到两个分句），或者换一个生成模型家族，再看盲测数字。
- **标签噪声高**：抽样审计认为 r1 一半、r2 近三成的生成标签有问题；修复前标出数里因此混有本来就不该标出的说法。没有人工标注者，无法给出人与模型的一致性。
- **分句限制**：规则按分句匹配，“宣称在一个分句、对象在另一个分句”的说法（两轮共 6 条被这样拒绝）需要跨分句的模型或更宽的窗口；后者会增加误报，本轮没有做。
- **决定由仓库作者做出**，不是法务；“需要人判断”的说法一律不采纳，所以每轮都有相当一部分漏检会留着。
- **盲测集保持未读**：只看了指标。如果以后读了其中的脚本或据此修改规则，此后的数字都不再是盲测，需要新的盲测集。

## 8. 截图与字幕 OCR（v1.3）

### 8.1 评测协议（在任何 OCR 打分之前提交）

机器可读版本：`backend/evals/ocr/protocol.json`。本节和它一起提交，早于任何一次 OCR 打分；之后对协议的任何改动都在 8.6 逐条列出。

**要回答的问题。** 访客上传广告截图、海报或几张视频帧，浏览器识别图中文字，再交给和粘贴文字时**同一个**规则引擎。和直接粘贴文字相比，丢了多少问题、多出多少误报、标出的框是否指在图上正确的位置、要多久。

**被测的引擎（ocr-1）。** PP-OCRv5 mobile 检测 + 识别（PaddlePaddle，Apache-2.0；ONNX 转换 `webnn/PP-OCRv5-ONNX` @ `006b441`），onnxruntime-web 1.30.0（MIT），WebAssembly SIMD 单线程，不用 WebGPU。运行时和权重按版本与 SHA-256 固定（与 CreditLens 0.35 是同一组文件和哈希），共 35,654,502 字节；权重在 Actions 构建时复制进本站，页面再校验一次 SHA-256。检测与识别之后的“按行排序、拼接成文本、把字符映射回图上的框”是本项目的代码。只有 `protocol.json` 里 `dev_tunable` 列出的参数和代码可以在 dev 上调整；跑 test 之前冻结，冻结提交写在 8.6。

**渲染（全部 SYNTHETIC）。** 在 GitHub Actions 的 Chromium 里用 canvas 绘制，不在本机运行：

| 版式 | 尺寸 | 内容 |
|---|---|---|
| 字幕帧 | 1280×720 | 一张图一条字幕：SRT 用例每条字幕一帧；文字用例在句末标点处切开，超过 36 字再在逗号处切，每行最多 18 字、两行；白字黑描边或半透明底框两种样式，字号 44 px |
| 海报 / 截图 | 1080×1440 | 整段脚本按段落排版，正文 40 / 30 / 22 px 三档，放不下就续到下一张 |

- 字体 4 种（Ubuntu 软件包）：Noto Sans CJK SC、Noto Serif CJK SC、文泉驿正黑、AR PL UKai（楷体）。缺字体时任务失败，不悄悄换成后备字体。
- 背景 4 种：浅色、深色、渐变、杂乱（固定种子的随机图形和噪声）。
- JPEG 质量 3 档：0.92、0.70、0.45（由 canvas 编码，识别的是解码后的 JPEG）。
- 分配：每个集合、每种版式内按用例编号排序；完整的因子网格（字体 × 背景 × JPEG × 样式或字号）用种子 20261110 洗牌，第 k 个用例取第 k 格（循环）；同一用例的多张图条件相同。每个用例两种版式各渲染一次。
- 真值：每张图上实际画出的字符串，以及每个字符由 `measureText` 得到的框。

**集合。**

| 用途 | 集合 | 规则 |
|---|---|---|
| dev | 原评测集 dev 30 条 | 调参，跑多少次都可以，可以看输出 |
| test | 原评测集 test 30 条、v1.1 盲测集 60 条、盲测集 v2 60 条 | 在冻结的引擎上只跑一次，第一次就是结果。盲测集 v2 只记录编号和数字，任务不写出它的脚本文字或识别文字，没有人打开它的渲染图 |

**三份参照。** 同一个浏览器引擎分别审：T0 = 评测集里的原文（现在的文字路径）；T1 = 图上实际画出的文字（加上版式的拼接，没有识别错误）；T2 = OCR 识别出的文字。T1、T2 的片段都换算回原文坐标再比较：T1 用渲染器的字符映射，T2 先和画出的文字做编辑距离对齐，再用同一映射。匹配规则与第 2 节相同：分类相同且字符 IoU ≥ 0.5，一对一贪心。

**指标。**

- **字符准确率**：1 − 编辑距离之和 / 参照字符数之和，按图累计；两边都做 NFKC 并去掉空白，标点计入。
- **保留率**：版式保留 = T0 的发现被 T1 匹配的比例；OCR 保留 = T1 被 T2 匹配的比例；**总保留 = T0 被 T2 匹配的比例**，即和直接粘贴文字相比访客得到多少。
- **OCR 引入的发现**：T2 里匹配不到任何 T1 发现的条数，占 T2 的比例。
- **干净渲染被标出**：没有金标片段、T0 也没有发现的用例，其渲染图在 T2 里至少有一条发现的比例。
- **框定位**：与 T1 匹配上的 T2 发现，它在每张图上的框与同一批字符画出时的框的并集 IoU ≥ 0.5 的比例。
- **金标 P / R / F1**：T0 与 T2 各算一次（次要；盲测集 v2 的金标是未审核的模型标注）。
- **必要声明**：T0 与 T2 的“缺少必要声明”不一致的用例数（只报告）。
- **时延**：每张图从解码完成到拼好文字（检测、识别、拼接）的秒数，按版式报告 P50、P95；初始化秒数；下载字节数。
- **不变量**：每条 T2 发现的引文等于 OCR 文字的对应切片；标为已核对的法条引用都在快照里。

**小字探测（描述性，不计入门槛）。** 每条 dev 用例的第一句画在 1080 px 宽的浅色截图条上，字号 10、12、14、16、18、20、24 px（Noto Sans CJK SC，JPEG 0.92），报告各字号的字符准确率；字符准确率达到 95% 的最小字号作为页面上“小字下限”的依据。

**发布门槛**（三个 test 集合并、全部条件、冻结引擎上的第一次 test 运行；全部满足才显示）：

| 指标 | 门槛 |
|---|---|
| 字符准确率 | ≥ 95% |
| 总保留率 | ≥ 90%，且每种版式 ≥ 85% |
| OCR 引入的发现 | ≤ 3% |
| 干净渲染被标出 | ≤ 2% |
| 框定位 | ≥ 95% |
| 每张图 P95 时延（Actions，单线程 WASM） | 字幕帧 ≤ 6 秒，海报 ≤ 20 秒 |
| 初始化 · 下载 | ≤ 15 秒 · ≤ 40 MB |
| 不变量 | 每一条都成立 |
| 真实 OCR 的访客流程检查 | 1440 与 375 px、浅色与深色全部通过 |

**决定。** 全部满足：工作台显示“图片 / 截图”输入，Pages 构建带上权重。任何一项不满足：公开构建不含这个输入，也不部署权重；数字照样写进本节和 CHANGELOG。各条件（字体、背景、JPEG、字号）的分项只报告，不作门槛。

**事先写明的局限。**

- 渲染图比真实广告干净：没有实拍背景、运动模糊、倾斜、弧形或竖排文字、艺术字、贴纸和水印叠加；字幕保留了标点，真实字幕常常没有。
- 只测文字。说出来的话（口播、配音）、画面本身（对比图、白大褂、徽章等视觉暗示）不在 OCR 的范围内，页面会写明。
- 参照是同一个规则引擎在原文上的结果，衡量的是“换成图片输入损失多少”，不是审查质量；审查质量仍以第 7.5 节盲测集 v2 的文字结果为准。

**发现了什么。**

- 第一版在海报上整字丢失，而且置信度接近 1：“到手价”读成“到价”，“医生”读成“医”，“月入过万”读成“入过万”。丢的多是笔画简单、在字表里排在前面的字（手、用、月、一、方、生），字表序号 100–299 的字删除率约 12%，其他区间约 1%。
- 先猜是识别器输入宽度固定、长行被压扁，于是把长行分段识别；日志显示两个模型的输入宽度都是动态的，这个猜测不对，分段也没有改善海报。
- 对照实验里，识别前把文字框左右各放宽 0.3 倍行高，总保留率从 88.8% 升到 94.8%（海报 82.8% → 94.8%），OCR 引入的发现从 1.9% 降到 0。关掉缩放平滑、DB 外扩系数 2.0 也有类似作用；换 RGB 通道顺序、分段都没有用。
- 识别器偶尔把简体字读成繁体（别 → 別、烟 → 煙、换 → 換、温 → 溫），规则按简体写，于是漏掉“别人家的……以次充好”这类问题。加了一步繁体转简体：OpenCC 的 TSCharacters 字表（Apache-2.0，提交 `fae2a0a`），只取 PP-OCRv5 字表里的单字，OpenCC 认为本身也是简体写法的字（如“乾”）不转。

**选定的设置**（`f7f0bad`）：左右放宽 0.3 倍行高 + 繁体转简体，缩放平滑保持“high”，不分段。关掉平滑在 dev 上多保留 1 处问题（97.4% 对 96.6%），但最近邻缩放对真实照片风险更大，所以没有采用。
