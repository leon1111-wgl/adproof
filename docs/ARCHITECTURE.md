# 架构设计

## 1. 设计目标

1. **可核对**：每条结果都能被人在几秒内核实：原文第几个字、哪条规则、哪部法律哪一条的原文。
2. **可复现**：同样的脚本、规则库版本和模型，得到同样的结果；每条审查记录保存规则库哈希、模型和商品资料快照。
3. **可降级**：模型不可用时，审查继续用规则完成，并在链路中标明。
4. **人做最后决定**：系统给出证据和建议，审核员决定通过、修改还是驳回。

## 2. 流水线与 Agent 契约

编排器 `app/agents/pipeline.py` 是一个**纯函数式**的流水线：输入商品资料和脚本，输出结构化结果，不碰数据库。API 层（`review_service.py`）负责持久化；评测（`evals/runner.py`）直接复用同一个流水线，所以“线上跑的”和“评测测的”是同一份代码。

| 步骤 | 类 | 输入 | 输出 | 失败策略 |
|---|---|---|---|---|
| 卖点提炼 | `SellingPointAgent` | 商品资料 | `[{title, detail, source_field, evidence}]` | 模型失败：直接由资料字段生成（span 标记“已降级”）；`evidence` 在资料中找不到的卖点被丢弃并写入 span |
| 脚本生成 | `ScriptWriterAgent` | 资料 + 卖点 + 体裁 / 风格 | 脚本文本 | 模型失败则整次运行失败（没有脚本就没法审） |
| 规则审查 | `RuleReviewer` | 脚本 + 商品类目 | 候选片段（rule / fact）+ 必要声明检查 | 规则引擎是确定性代码，异常即缺陷，不降级 |
| 模型审查 | `ModelReviewer` | 脚本 + 类目说明 | `[{quote, category, reason}]` | `LLMError` → 返回空结果并标记“已降级”，规则通道照常 |
| 证据定位与校验 | `EvidenceLocator` + `validate_findings` | 两个通道的候选 | finding 列表、被拦截的引用、校验报告 | 不修复，只丢弃并记录原因 |
| 改写建议 | `RewriteAgent` | finding + 必要声明 | 字符级编辑列表 | 模型改写不合格时回退到规则模板 |
| 复审 | 同“规则审查 ∥ 模型审查 → 证据定位” | 改写稿 | 剩余 finding | 最多 `ADPROOF_REWRITE_MAX_ROUNDS` 轮（默认 2） |
| 人工终审 | `review_service.decide` | 审核员决定 | 终审状态、终稿 | 规则见第 6 节 |

Agent 之间传递的是普通的 dict / dataclass，每个字段在代码中有明确含义；模型的输出一律先解析成 JSON（`parse_json_object` 接受裸 JSON、代码块和夹在文字中的对象，失败时追问一次），再由下游校验，而不是直接信任。

### 并行与链路

两个审查通道在 `ThreadPoolExecutor` 中并行执行。SQLAlchemy 的 Session 不是线程安全的，所以 span 先在内存中加锁缓冲，由编排线程在每个阶段结束后 `flush()` 写库；前端轮询审查详情，就能看到流水线逐步推进。人工终审完成时，系统在同一条链路末尾追加一个 `human_review` span，记录决定、版本和备注。

## 3. 证据定位

### 3.1 归一化与位置映射（`textutil.normalize`）

规则和模型引用都在归一化文本上匹配：NFKC（全角转半角）、英文小写、去掉空白和零宽字符、去掉夹在两个汉字之间的装饰符号（`最*好*用`、`第·一`）。归一化时为每个字符记录它在原文中的下标，所以匹配到的位置可以精确映射回原文，`quote` 永远是原文的原样切片（例如“最 好 用”“ＮＯ．１”）。

### 3.2 模型引用的定位

1. 精确查找 `quote`，可能出现多次，每次出现都生成候选；
2. 找不到时，在归一化文本中查找归一化后的 `quote`（模型常把全角标点改成半角、去掉空格）；
3. 仍找不到：拦截，记入 `rejected`（原因“原文中找不到该片段：模型可能改写或编造了引用”），界面上单独提示，不作为结果展示；
4. 分类不在规则库中的、缺少 `quote` 的，同样拦截。

### 3.3 合并

候选按位置排序后分组：

- **同一分类、有重叠** → 合并为一条，片段优先取规则 / 事实通道的（更精确），再取最长的；
- **不同分类、重叠超过较短片段的 60%** → 合并为一条，保留优先级更高的分类（YAML 中的 `priority`），其余记为 `related_categories`；
- 合并后记录来源通道（`rule` / `fact` / `llm`），界面上显示为“规则 / 事实核对 / 模型”。

### 3.4 法律依据解析

依据由“分类的依据 + 规则补充的依据”组成，并按商品类目过滤（`when`）。例如疾病治疗类：始终引用《广告法》第十七条；保健食品追加第十八条第一款第二项；食品追加《食品安全法》第七十三条第一款；化妆品追加《化妆品监督管理条例》第四十三条第二款。罚则单独列出（`kind: penalty`）。

`LawLibrary.resolve` 只从本地快照取原文；条、款、项任何一级在快照中不存在，就返回 `status: pending`、正文为空、备注“原文待核对”。

### 3.5 独立校验（`validate_findings`）

不管结果来自哪个通道，最后都要过一遍：

- `0 ≤ start < end ≤ len(text)`，且 `text[start:end] == quote`；
- 分类存在于当前规则库；
- 每条标记为 `verified` 的引用，其正文必须能在本地快照的对应条文中找到。

任何一项不满足，这条结果就被丢弃并写入校验报告。测试里专门构造了“改过的引用片段”和“编造的法条原文”两种篡改，确认都会被拦下。

## 4. 商品事实核对（`rules/facts.py`）

从商品资料中解析“数字 + 单位”（价格、成分含量、规格、续航、功率等），再在脚本中找同单位的数字：同一分句提到了资料里的属性词（如“烟酰胺”“续航”“到手价”），而数字与资料中所有同单位的值都不一致，才判为不一致。W、mAh、dB 这类单位本身就说明了属性，资料中只有一个同单位的值时不要求属性词。改写时直接用资料中的数字替换。

这一类结果的证据是“脚本片段 + 商品资料原文”两部分，都能核对。

## 5. 改写

改写是**字符级的最小编辑**，不是整篇重写：

1. 商品事实不一致：把脚本中的数字换成资料中的数字；
2. 规则库中有替换模板（如“全网最低价”→“直播间活动价”、“消炎”→“舒缓”）：按模板替换；
3. 子串替换、正则替换、前缀替换（“最好用”→“很好用”）；
4. 否则删除所在分句，并顺带去掉多余的逗号；
5. 缺少必要声明：在结尾追加（如“本品不能代替药物。”）。

重叠的编辑会合并：删除分句会吞掉分句内的其他替换。编辑按位置倒序无冲突地应用，并输出字符级 diff，界面上用删除线和高亮展示。diff 由各轮编辑直接合成（哪些字被改是已知的），只在每个改动区域内用 difflib 做细粒度对齐；对整篇跑 difflib 在重复型长脚本上是平方级以上，6000 字时要几分钟（v1.1 修复）。接入真实模型时，改写 Agent 会把模板结果作为提示交给模型润色；模型的改写只有在“不再包含原违规片段、长度合理、单独过一遍规则引擎没有命中”时才会被采用。

## 6. 人工终审规则

| 决定 | 前提 |
|---|---|
| 采用改写稿通过 | 改写稿复审通过（没有高、中风险问题，必要声明齐全） |
| 原稿通过 | 每个高、中风险 finding 都被审核员标记为误报（必须写理由），且没有缺少的必要声明 |
| 修改后通过 | 修改稿用同一套审查复检通过；复检本身也是一条链路（`kind = recheck`） |
| 驳回 | 必须写原因 |

所有决定都遵守四眼原则：提交人不能终审自己的脚本。审核员对每条 finding 的“确认 / 误报”会按规则聚合成命中数和误报率，显示在规则库页面，作为调整规则的依据。

## 7. 数据模型

| 表 | 说明 |
|---|---|
| `users` | 演示账号与角色（admin / reviewer / operator） |
| `products` | 商品资料（事实以键值对存储） |
| `reviews` | 审查记录：输入、字幕时间轴、商品快照、卖点、必要声明、改写结果、被拦截的引用、校验报告、规则库版本与哈希、模型、终审信息 |
| `findings` | 每条结果一行，含审核员判定，方便按规则统计误报 |
| `runs` / `spans` | 链路：一次运行、每个 Agent 步骤 |
| `eval_runs` | 评测记录（指标 + 逐条结果） |
| `audit_events` | 判定、终审、规则库保存的审计日志 |

## 8. 规则库热更新

规则库是一个 YAML 文件。管理员在控制台保存时，后端依次检查：YAML 语法与字段（Pydantic）、每个正则能否编译、每条规则自带的正例必须命中且反例不能命中、法条引用能否在快照中解析（解析不了的作为“待核对”警告）。检查通过才写回文件并替换内存中的规则集；新的审查记录会带上新的规则库哈希，旧记录保留当时的哈希。

## 9. 模型适配

- `LLMProvider.chat(messages, task=...)`：所有 Agent 只依赖这个接口。
- `OpenAICompatProvider`：豆包（火山方舟）、混元、DeepSeek 的 OpenAI 兼容接口；默认请求 JSON 模式，HTTP 400 时去掉 `response_format` 重试一次；408 / 409 / 429 / 5xx 和网络错误指数退避重试；没有返回用量时按字符估算并标注“估算值”。
- `MockLLM`：离线确定性模型，实现同样的 JSON 契约，让演示、测试和 CI 不依赖 API Key。它的“语义审查”只是一组上下文模式，用来跑通双通道流程，不代表模型能力。

## 10. 静态演示的浏览器引擎（v1.1）

```
访客脚本 ──► frontend/src/engine/（TypeScript）──► 与 API 相同结构的审查记录 ──► 同一套批注稿 / 改写 / 签发界面
                  ▲
   pack.json ◄── scripts/build_browser_pack.py ◄── backend/rules/*.yaml · backend/laws/*.json · 离线语义模式
                  │
   tests/parity.test.ts ◄── scripts/export_parity_fixtures.py（后端在 528 个输入上的输出）
```

- **范围**：卖点提炼（离线）、规则审查、商品事实核对、离线语义模式、证据定位与校验、条款引用、模板改写与两轮复审、修改稿复检、规则试运行。脚本生成仍回放录制结果。
- **偏移**：后端按码点，浏览器按 UTF-16。引擎输出 UTF-16 偏移，界面可以直接切片；比较长度的地方（去重、合并、主片段、编辑排序）按码点计，与后端一致。
- **引擎标注**：`src/demo.ts` 给每条审查记录、复检和规则试运行附上 `engine`（回放 / 浏览器内），审查页顶部显示。
- **审查范围**：`src/engine/scope.ts` 生成默认不放行的说明，是演示层自己的内容，不改变任何结果。
- **模拟签发**：逐条判定和终审只改页面内存，规则与第 6 节相同（`tests/signoff.test.ts`）；提交人可以一键切换为审核员继续。
- **不包含**：浏览器端语言模型（理由见 [FRONTIER_REVIEW.md](FRONTIER_REVIEW.md)）。

## 11. 红队回合（v1.2）

```
.github/workflows/redteam.yml（Actions，4 核 CPU，llama.cpp；只读权限，不提交任何东西）
  生成  GLM-4-9B-0414 ──► round.json（每类违规说法 + 合规近似说法；JSON Schema 约束）
  打分  frontend/scripts/redteam-score.ts（这次提交的浏览器引擎）──► scores.json（修复前）
  审计  Qwen3-4B-Instruct-2507 ──► audit.json（固定随机抽样 → 标签噪声；漏检 / 误报 → 分诊）
  提案  python -m app.redteam proposals ──► proposals.md（每条漏检可引用的已核对条款）
                     │ 下载产物，提交到 backend/evals/redteam/rN/
作者（单线程写入）    decisions.json ──► 规则库单独提交 ──► score --append ──► rescores.json
                     │
python -m app.redteam report ──► frontend/src/redteam-report.json ──► 页面“红队回合”
python -m app.redteam blind  ──► blind_runs.json（盲测集 v2 的片段指标，不含脚本原文）
```

- **谁写什么**：生成模型和审计模型只产出文本和标签，进不了规则库；规则库只由作者的单独提交修改，新规则只进入已有分类，所以引用只来自已核对快照。
- **可复现**：权重、llama.cpp 按 URL 与 SHA-256 固定；每轮记录种子、生成参数、Actions 运行编号、提交和吞吐。模型输出在不同硬件上不保证逐字相同，所以每轮的产物原样提交，页面只读提交过的文件。
- **一致性检查**：`tests/redteam.test.ts` 要求页面的“当前结果”就是这次构建的引擎的结果、最后一次重审用的就是这次构建的规则库、修复前标出的说法没有退化、每条漏检都有决定；`tests/test_redteam.py` 检查抽样固定、噪声率计算、提案只列适用且已核对的条款、页面数据不过期。
- **本地**：不在本机运行任何模型。`pnpm exec vite-node scripts/redteam-score.ts -- 文件.json` 可以用引擎审任意一组说法（确定性代码）。
